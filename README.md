# CRM

## Описание

Внутренняя CRM-система для работы с заявками (лидами), клиентами и задачами: Kanban-доска, дашборд с аналитикой и управление сотрудниками.

## Технологический стек

- **Фреймворк**: Next.js 16 (App Router), React 19, TypeScript
- **Стилизация**: Tailwind CSS v4
- **База данных**: Turso (libSQL/SQLite) через `@libsql/client`
- **Аутентификация**: собственная, JWT (`jose`) в httpOnly-cookie, пароли — `bcryptjs`
- **Drag-and-drop**: `@dnd-kit/core`
- **Графики**: `recharts`

## Роли пользователей

| Роль | Доступ |
|------|--------|
| **admin** | Видит все заявки, клиентов и задачи; управляет сотрудниками; видит аналитику по всей компании, включая сравнение сотрудников |
| **manager** | Видит и редактирует только назначенные на него заявки и задачи; может создавать клиентов и заявки; аналитика только по его заявкам |

Роль проверяется на уровне API: каждый защищённый route сам сверяет права, а не полагается на то, что интерфейс не показал кнопку.

## Установка и запуск

```bash
npm install
cp .env.example .env.local   # затем заполнить переменные
npm run db:migrate           # создать таблицы
npm run db:seed              # создать первого администратора
npm run dev                  # http://localhost:3000
```

## Переменные окружения

| Переменная | Описание |
|------------|----------|
| `TURSO_DATABASE_URL` | `file:local.db` для локальной разработки или `libsql://...` для облака |
| `TURSO_AUTH_TOKEN` | Токен Turso; для локального файла оставить пустым |
| `AUTH_SECRET` | Секрет подписи JWT |
| `SEED_ADMIN_NAME` | Имя первого администратора |
| `SEED_ADMIN_EMAIL` | Email первого администратора |
| `SEED_ADMIN_PASSWORD` | Пароль первого администратора, не короче 8 символов |

Сгенерировать `AUTH_SECRET`:

```bash
node -e "console.log(require('crypto').randomBytes(48).toString('base64url'))"
```

## Скрипты npm

- `dev` — сервер разработки
- `build` — production-сборка
- `start` — запуск собранного приложения
- `lint` — проверка ESLint

## Страницы

- `/login` — вход
- `/dashboard` — аналитика
- `/leads` — Kanban-доска заявок
- `/leads/[id]` — карточка заявки
- `/clients` — список клиентов с поиском
- `/clients/[id]` — карточка клиента с историей заявок
- `/tasks` — задачи
- `/profile` — свой профиль: имя, почта, пароль, аватар
- `/users` — сотрудники (только для admin)

## Аватары

Аватар задаётся двумя способами и хранится в колонке `users.avatar_url`:

- **файлом с компьютера** — картинка обрезается по центру и уменьшается до 256×256 прямо в браузере, на сервер уходит уже `data:image/webp` весом в десятки килобайт (серверный предел — 400 КБ);
- **ссылкой из интернета** — сохраняется сам адрес, картинка каждый раз грузится с чужого сайта. Если её там удалят, аватар пропадёт.

Отдельного хранилища файлов нет специально: так проект остаётся на одной Turso и разворачивается на Vercel без дополнительных сервисов.

## Приём заявок с сайта

Форма обратной связи на сайте может слать заявки прямо в CRM.

```
POST https://<домен-crm>/api/public/leads
X-Api-Key: <INTAKE_API_KEY>
Content-Type: application/json

{ "name": "Алишер", "phone": "+998901234567", "email": "a@example.uz", "message": "Текст обращения" }
```

- `name` обязателен, плюс хотя бы одно из `phone` / `email`; `message` необязателен.
- Ответ: `201 {"ok":true,"leadId":"...","clientCreated":true}`.
- Клиент ищется по телефону, затем по почте — повторные обращения одного человека не плодят дубликатов.
- Заявка попадает в колонку «Новая» с источником «Форма на сайте» и без исполнителя: её разбирает администратор.

Защита: ключ `INTAKE_API_KEY`, не более 10 запросов с одного адреса за 10 минут, и список
доменов `INTAKE_ALLOWED_ORIGINS` — он нужен, только если форма отправляется прямо из браузера
посетителя. Тогда ключ виден в коде страницы, поэтому надёжнее отправлять запрос с сервера сайта.

## Переход на Turso

1. Создать базу в Turso.
2. Подставить её URL и токен в `.env.local`.
3. Повторно выполнить `npm run db:migrate` и `npm run db:seed`.

Код менять не нужно.

## Ограничения MVP

- Сессия — один JWT без refresh-токена и без принудительного разлогина: деактивированный сотрудник с уже выданным токеном сохраняет доступ до истечения срока (7 дней). Новый вход ему при этом закрыт.
- Нет ограничения частоты попыток входа.
- История изменений заявки не хранится — только текущее состояние и заметки.
- Нет email- и push-напоминаний о задачах, только визуальная подсветка просроченных.
- Первый администратор создаётся скриптом, а не через интерфейс, чтобы никто не мог сам назначить себе роль администратора.
